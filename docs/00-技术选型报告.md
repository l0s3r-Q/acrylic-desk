## 2. 杀软拦截的真实归因

这一节是选型的核心依据，**纠正一个常见误解**。

### 2.1 结论先行

> **框架本身不是杀软误报的主因。真正的主因是「安装器行为特征」+「代码签名缺失」。**

杀软的启发式引擎（尤其国产 360 / 火绒 / 腾讯电脑管家）主要依据以下行为打分：

| 行为特征 | Electron | Tauri | .NET/WinUI |
|---|---|---|---|
| 释放大量子进程（`node.exe` 特征） | ❌ 严重 | ✅ 无 | ✅ 无 |
| 自解压安装器释放数百个文件到 `%AppData%` | ❌ 严重 | ⚠️ 视打包方式 | ⚠️ 视打包方式 |
| 写入 `Run` 注册表键做自启 | ⚠️ 常规 | ⚠️ 常规 | ⚠️ 常规 |
| 释放的 exe 无签名 | ❌ 极高风险 | ❌ 高风险 | ❌ 高风险 |
| 内嵌浏览器内核（WebView2 依赖） | ✅ 自带 Chromium | ✅ 共用系统 WebView2 | ✅ 共用系统 WebView2 |
| 体积 | 150 MB+ | 8–15 MB | 40–80 MB |

### 2.2 关键事实

1. **Electron 误报率最高的原因**：安装后目录里出现一个完整的 `node.exe` / `electron.exe`，
   且会派生子进程。国产杀软的"远控木马"启发式规则对这类形态极度敏感 —— 这也是为什么
   `xxx-setup.exe` 未签名时几乎必然触发 360 拦截。

2. **Tauri 的天然优势**：编译产物是**单个原生 exe**，运行时复用系统已装的 WebView2
   （本机已确认安装 `154.0.4258.62`）。没有 Node 运行时、没有子进程树、
   没有自解压释放过程。行为特征接近普通原生程序。

3. **绿色版 > 安装版**：解压即用的绿色版（portable）跳过了"安装器写入系统目录"这一
   杀软重点监控环节，是**规避误报最有效的单一手段**。

4. **代码签名是终极解法，但非必需**：EV 证书可让 SmartScreen 立即放行，
   但年费数千元。对于自用/小范围分发，**绿色版 + 提交误报申诉**已足够。

### 2.3 本项目的应对策略

```
第一层：单文件原生 exe，不打包安装器（portable 模式）
第二层：不写入注册表自启，改用启动文件夹快捷方式（可选，默认关闭）
第三层：所有文件操作走 Rust 标准 API，不动态生成/加载可执行代码
第四层：提供 SHA256 校验值，附送杀软白名单添加指北
第五层（可选，未来）：购买代码签名证书
```

详见 [08-分发与防误报指南](./08-分发与防误报指南.md)。

## 4. 关键技术验证（已实测）

### 4.1 Tauri 内置亚克力支持 —— 从源码确认

下载 `tauri-utils 2.10.1` 源码包，读取 `src/lib.rs` 中 `WindowEffect` 枚举定义：

```rust
pub enum WindowEffect {
    // ... macOS 系列 ...
    /// Mica effect that matches the system dark preference **Windows 11 Only**
    Mica,
    MicaDark,
    MicaLight,
    /// Tabbed effect ... **Windows 11 Only**
    Tabbed,
    TabbedDark,
    TabbedLight,
    /// **Windows 7/10/11(22H1) Only**
    /// ## Notes
    /// This effect has bad performance when resizing/dragging the window
    /// on Windows 11 build 22621.
    Blur,
    /// **Windows 10/11 Only**
    /// ## Notes
    /// This effect has bad performance when resizing/dragging the window
    /// on Windows 10 v1903+ and Windows 11 build 22000.
    Acrylic,
}
```

**结论**：`Acrylic` 是官方枚举值，无需手写 Win32 P/Invoke。配置写法：

```json
{
  "app": {
    "windows": [{
      "transparent": true,
      "decorations": false,
      "effects": {
        "effects": ["acrylic"],
        "state": "active",
        "radius": 12
      }
    }]
  }
}
```

### 4.2 ⚠️ 源码揭示的性能陷阱

官方注释明确指出：

> `Acrylic`: This effect has bad performance when resizing/dragging the window
> on Windows 10 v1903+ and Windows 11 build 22000.

**这是真实存在的坑**，DeskBox 用"材质降级"绕开了它。本项目采用的应对策略：

| 场景 | 材质 | 理由 |
|---|---|---|
| 静态显示 | `Acrylic` | 视觉最佳 |
| 滑入/滑出动画期间 | 临时切 `Blur` 或纯色 | 避开 Acrylic 重绘开销 |
| 用户拖拽调整面板时 | 临时切 `Blur` | 同上 |
| 动画结束 | 恢复 `Acrylic` | — |

实现方式：Rust 侧暴露 `set_window_effect(effect)` 命令，前端在动画开始/结束的生命周期钩子里调用。

## 6. 最终决策

**采纳方案 C：Tauri 2 + Vue 3 + TypeScript + Vite**

理由汇总：

1. ✅ 唯一同时满足"低杀软误报 + 真亚克力 + WebUI 自由度"三重要求的方案
2. ✅ 亚克力为框架内置能力，非 hack 实现，长期可维护
3. ✅ 本机环境已就绪，仅缺一个 CLI（正在安装）
4. ✅ 分发体积 8–15 MB，内存占用 60–120 MB，符合常驻软件定位
5. ✅ Rust 侧对 Win32 API 的调用能力，使"碰边唤出"能做到最高精度

**已知代价**：

- Rust 学习/调试成本高于纯 JS（但本项目 Rust 代码量可控，约 1500–2500 行）
- WebView2 需系统安装（Win 11 已内置，Win 10 需引导安装）
